# Робота агента в DatasetCreator

## Керування й делегування

Головний агент — менеджер: він визначає межі задачі, остаточний план, критерії прийняття, інтегрує результати й перевіряє сукупний diff. Використовуй спеціалістів із локальної `.codex/agents/`, коли потрібна їхня роль; ця інструкція дозволяє делегування, але не вимагає запускати всі ролі для кожної задачі. Явне прохання лише обговорити або спланувати не дозволяє змінювати файли.

- Передавай короткий пакет контексту: мета, релевантні докази, точні дозволені шляхи, заборонені дії, критерії прийняття, потрібні перевірки та дозвіл або заборона коміту. Не передавай повну історію чату, якщо достатньо цього пакета.
- Незалежним агентам призначай непересічні шляхи запису; залежні зміни виконуй послідовно. Перевикористовуй наявний контекст спеціаліста, коли він відповідає задачі.
- Спеціалісти не делегують далі. Дефекти від tester передаються менеджеру, який призначає виправлення developer і перевіряє результат.
- Не додавай супутніх покращень і не розширюй межі задачі мовчки. Про блокери та необхідні зміни поза призначеними межами повідомляй менеджеру.
- Якщо клієнт не підтримує вибір іменованої ролі, менеджер читає відповідний TOML і явно передає інструкції, модель та reasoning effort агенту. Локальні визначення не комітяться; якщо їх немає, використовуй межі ролей і профілі нижче.

| Роль | Дозволені зміни | Результат |
| --- | --- | --- |
| scraper | Жодних файлів або комітів | Цільові факти, шляхи й номери рядків, явні невідомі |
| architect | Жодних файлів або комітів | Архітектурний аналіз і план у чаті |
| developer | Призначений код, UI та ресурси, переважно `src/` | Реалізація та її перевірка |
| tester | Призначені тести, fixtures і допоміжний тестовий код, переважно `tests/` | Тести, результати запуску та відтворювані дефекти |
| tech_writer | Призначена документація: `docs/`, README та основні документи тем | Документація за фактичним остаточним diff |

Tech writer не редагує коментарі коду або docstrings. Tester не виправляє продуктовий код і не послаблює тести, щоб приховати дефект. Architect і scraper не створюють навіть тимчасових файлів і не виконують команди, що змінюють стан проєкту. Спеціалісти не редагують `AGENTS.md` чи власні визначення ролей. Це поведінкові межі, а не окремі файлові sandbox; менеджер перевіряє їх дотримання.

Типові профілі: scraper — `gpt-6-luna` / `low`; developer, tester і tech_writer — `gpt-6-sol` / `medium`; architect — `gpt-6-sol` / `high`. Явні побажання користувача мають пріоритет. Reasoning effort не є фіксованим бюджетом токенів. Якщо модель недоступна, повідом менеджеру; не обирай дорожчу мовчки.

## Мінімальний контекст

1. Перевір `git status --short`; збережи чужі незавершені зміни.
2. Прочитай [карту коду](docs/code-map.md), потім лише цільовий модуль, його call sites і відповідний тест.
3. Для загальної структури дивись [архітектуру](ARCHITECTURE.md); для форматів — [модель даних](docs/data-model.md); для команд — [розробку](docs/development.md).
4. Не читай весь `App.tsx`, усі тести або `plan.md` за замовчуванням. Починай із `rg` за символами та обмежених фрагментів. Документація — карта, поточний код — доказ.

Не читай масово `node_modules/`, `dist/`, кеші, звіти тестів, великі JSON/manifest чи бінарні моделі. Для діагностики бери лише потрібний фрагмент. Manifest та індекси є частиною моделі даних: не ігноруй їх у Git і не переписуй без потреби. Для широкого пошуку спершу доручи scraper конкретне питання; типовий звіт — до 600 слів із короткими витягами та посиланнями. Менеджер може замовити докладніший звіт.

## Перевикористання та інваріанти

- Перш ніж додавати helper, шукай функцію і всі її використання. Розширюй наявного власника поведінки, а не копіюй логіку між tools.
- Dataset один; членство визначає фізичний шлях у `dataset/`. Не відновлюй паралельні списки ID, legacy exclusion flags або Dataset caption overrides як новий механізм.
- Для галерей використовуй `workspaceImages`/`workspaceFileAssets`, для підписів — caption resolver/mutation service, для експорту — export plan.
- Файлові зміни координуй через `runProjectFileOperation`. Усередині exclusive callback не викликай `flushProjectSave` і не запускай вкладену exclusive-операцію; спершу перевір, чи wrapper уже є у виклику.
- Зміна шляху має оновлювати посилання, вкладки, Explorer і файловий кеш. Використовуй наявні path-move helpers.
- Збережений baseline просувається лише після успішного запису; старий проєкт не повинен оновлювати стан нового.
- `tags: []` і відсутні tags мають різний зміст. Blob URL не є постійним шляхом; звільняй його через наявний механізм власника.
- Не називай гістограмні ознаки DINOv2, а хешування тексту — мовною моделлю. Дивись окремих власників у карті коду.

## Завершення роботи

Запусти тематичні тести з `docs/development.md`, build для типів/UI; для значних змін — `npm run test:ci`. Компіляція browser fixtures не доводить проходження браузерних сценаріїв. Lint не налаштований.

Оновлюй лише основний документ теми та карту коду, якщо змінено власника логіки. Не дублюй довгі інтерфейси чи інструкції. У звіті вкажи фактичні перевірки й обмеження. `plan.md` не включай до комітів; додавай файли явно, а не через `git add .`.


## Git-дисципліна

- Завершений логічний етап коміть після відповідної перевірки й огляду менеджером, якщо користувач явно не заборонив коміти. Плануй ці контрольні точки заздалегідь; не відкладай усі коміти до кінця й не розділяй усю завершену задачу заднім числом.
- Спеціаліст комітить лише за явним дорученням менеджера; інакше перевірений етап комітить менеджер. Використовуй conventional commits відповідно до зміни, наприклад `feat:`, `fix:`, `test:` або `docs:`.
- Додавай лише явні шляхи з власними дозволеними змінами. Не використовуй `git add .` або `git add -A`; переглянь staged diff перед комітом.
- Якщо вже staged сторонні зміни, повідом про блокер. Не включай їх у свій коміт і не знімай їх зі staging самостійно.
- Не перезаписуй і не відкочуй роботу користувача чи інших агентів. Спеціалістам заборонені push, merge, amend, reset і clean.
- Локальні налаштування асистентів, ролі, сесії, пам’ять, `plan.md`, кеші та тимчасові результати не комітяться. Спільні `AGENTS.md`, документація, вихідні файли й тестові fixtures залишаються під контролем версій. `.gitignore` не прибирає вже відстежувані файли.

## Звіти спеціалістів

Кожен спеціаліст вказує виконану роботу або висновки, фактичні перевірки та результати, змінені файли (або їх відсутність), невирішені питання й блокери. Відділяй факти від гіпотез, наводь релевантні шляхи й рядки; не заявляй про проходження перевірки без її запуску.

Для дефекту tester надає проблему, передумови, кроки відтворення, очікувану й фактичну поведінку, докази (тест, помилка або лог) і можливі причини з місцями в коді. Позначай підтверджене та припущення окремо. Помилки середовища або налаштування не видавай за дефекти продукту.

# Розробка та перевірки

## Середовище

Використовуйте Node.js 22.22.1, як у тестовому workflow, та `npm ci` для встановлення за lockfile. Поточний Pages workflow окремо використовує Node 20; не плутайте його з тестовим CI. Для папок потрібен File System Access, для відео — підтримка WebCodecs; доступність функцій перевіряйте в реальному цільовому браузері.

| Команда | Результат |
| --- | --- |
| `npm run dev` | Vite dev server |
| `npm run build` | TypeScript і production-збірка в `dist/` |
| `npm run preview` | Перегляд зібраного застосунку |
| `npm test` | Усі сім офлайн-наборів, зупинка після першої помилки |
| `npm run test:ci` | Усі тести, build, компіляція браузерних стендів |
| `npm run test:browser-fixtures` | Збірка стендів із `vite.browser.config.ts` у `dist/browser-fixtures/` |

`npm run lint` наразі не є робочим gate: ESLint не налаштовано. Не заявляйте про успішний lint на підставі build. Попередження ONNX про `eval` і великі chunks можуть з’являтися під час збірки; їх потрібно відрізняти від коду завершення з помилкою.

## Вибір регресійних перевірок

| Зона зміни | Команда |
| --- | --- |
| Серіалізація, міграції, індексація, Explorer, Dataset-файли, версії | `npm run test:project-types` |
| Docking, геометрія, вкладки й відновлення layout | `npm run test:workspace-layout` |
| Вибір кадрів, індекс, скасування, fingerprints, запис PNG | `npm run test:video-frames` |
| Команди, підписи, імпорт/експорт, save queue, навігація | `npm run test:ui-workflows` |
| Кандидати, coverage, формування Dataset, міграція підписів | `npm run test:dataset-assembly` |
| Прев’ю, blob URL, snapshots, дозволи й класифікація файлів | `npm run test:service-boundaries` |
| Відновлення після помилок, concurrent saves, історія та операції | `npm run test:state-recovery` |

Скрипти в `tests/*.mjs` збирають потрібні TypeScript-модулі через Rolldown у тимчасову папку, виконують перевірки й прибирають bundle. Вони використовують справжню логіку застосунку з in-memory filesystem або симуляціями браузерних API. Нові тести для сервісів і стану використовують `node:test`; запускати їх можна через відповідні npm-команди.

Для нової регресії оберіть наявний тематичний набір. Перевіряйте видимий результат, порядок операцій, помилку або збережені дані. Для конкурентності використовуйте керовані promises, для timeout — контрольовані таймери; не прив’язуйте тест до випадкової швидкості машини. Не додавайте аналогічний helper або ще одну бібліотеку тестування без потреби.

## Межі автоматизації

Збірка браузерних стендів не виконує UI-assertions. Поточна конфігурація компілює explorer, export, persistence, caption і project-switch. Інші HTML-стенди в `tests/` відкриваються через dev server; наприклад `/DatasetCreator/tests/video-browser.html`.

Окремо перевіряйте native file picker, живий Photopea, фактичний ONNX inference, клавіатуру, фокус, zoom та доступність. Частина відеоперевірок завантажує модель і залежить від GPU/кодеків. [Історичний UI-звіт](../tests/ui-validation.md) містить відтворювані сценарії та їхні обмеження. Наявні тести не дають виміряного відсотка покриття всього коду.

## Робота зі зміною

1. Перегляньте `git status` і [карту коду](code-map.md). Визначте власника потрібної поведінки.
2. Прочитайте цільовий модуль і відповідний тест; перевірте наявні call sites функції.
3. Змініть одну спільну реалізацію, зберігши правила шляхів, Dataset, підписів і черги збереження.
4. Запустіть відповідний набір; для зміни типів або UI — також build. Перед передачею значних змін використайте `npm run test:ci`.
5. Оновіть основний документ теми. Не включайте `plan.md` та чужі незавершені зміни у свій коміт.

CI в `.github/workflows/tests.yml` запускає `npm run test:ci` на push і pull request. Pages workflow незалежний від нього: завершення Tests зараз не є залежністю deploy job. Подробиці — в [розгортанні](../DEPLOYMENT.md).
